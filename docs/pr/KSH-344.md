KSH-344: Sentinel: treat 401 on Oplox's protected log routes as a pass

Base: `main` @ bcf8703.

## What changed and why

Since Oplox KSH-247, `GET /api/logs` and `GET /api/logs/stream` answer 401 without an admin token. The canary only accepted 200, so it reported Oplox as broken (CRITICAL `CORE_API_UNAVAILABLE`) when it was working as intended, and with `--heal` could have acted on it.

* `probeApiEndpoints` takes paths or `{ path, expect }`; `expect: 401` passes on 401 and fails on 200 with `protectionMissing`. Plain paths behave as before (200 + JSON).
* `probeSseStream(baseUrl, endpoint, expect)`: `expect: 401` passes on 401; a public stream fails with `protectionMissing`. Default unchanged.
* New diagnosis `PROTECTED_ENDPOINT_PUBLIC` (CRITICAL, not self-healable) when a protected route answers 200, so a lost login guard turns the canary red, and it is no longer reported as an API outage.
* Profile: for `serviceName: 'oplox'` the default is `/api/apps` public JSON plus 401 on `/api/logs` and `/api/logs/stream`. Every other service keeps the old expectations. The `doctor` command uses the default instead of its own list.
* README documents the expected status per endpoint. The sentinel holds no admin token.
